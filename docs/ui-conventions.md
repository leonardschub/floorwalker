# Frontend conventions: accessibility and i18n

The contract for `web/`. It states the WCAG 2.2 AA bar every screen ticket inherits, the i18n rules the strings follow, the accessibility rules oxlint enforces, and a baseline audit of the pages that exist today. The enforced half lives in `.oxlintrc.json`; the inventory of what the app ships is in `features.md`.

## The bar: WCAG 2.2 AA

`web/` targets WCAG 2.2 Level AA, which includes every Level A criterion. A screen ticket is not finished while it introduces an AA failure, and every failure recorded in the baseline below has to be fixed by that ticket or carried forward with a written reason. These are the six areas a review looks at first, with the criteria that carry them.

- **Keyboard reachability** (2.1.1, with no trap under 2.1.2). Every control is reachable and operable from the keyboard alone, in an order that follows the visual order. Reach for a native `input`, `button`, `a`, `select` or `textarea`; a click handler on a `div` needs a role, a tabindex and key handlers of its own, which is the signal to use the element instead.
- **Visible focus** (2.4.7). Every focusable element shows an indicator that is visible against the surface it is drawn on. The pattern here is `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-focus`, the ring drawn in the accent token, as in `text-field.tsx` and `submit-button.tsx`. An outline drawn in the same colour as the surface behind it is not an indicator.
- **Text contrast** (1.4.3, at 4.5:1 for body text and 3:1 for large text, plus 1.4.11 at 3:1 for the non-text parts that identify a control, its state or a link). Check the token pair actually in use, on both the light and the dark surface, and do not eyeball it. This is the one item in the list that no linter can see.
- **Reduced motion** (2.2.2, 2.3.1). Anything that moves, fades or animates is removed or reduced under `prefers-reduced-motion: reduce`. Nothing in `web/src` animates today, so the rule binds from the first transition that gets added.
- **Semantic landmarks and accessible names** (1.3.1, 2.4.1, 4.1.2). One `main` per page, one `h1`, and `header`, `footer` and `nav` where the shape calls for them. When a page carries more than one `nav`, each one gets a name, as `site-footer.tsx:14` does for the footer. Every control has an accessible name that identifies it, not merely a name that exists.
- **Form labelling and error association** (1.3.1, 3.3.1, 3.3.2, 4.1.3). A visible label is associated programmatically, either by wrapping the input in the label as `text-field.tsx:25-36` does or by pointing at it with `htmlFor` and `id`. An error names the field it belongs to, is associated with that field through `aria-invalid` and `aria-describedby`, and any message that appears after submit goes into a live region that was already in the DOM before the message arrived.

Three further criteria bind and are easy to miss. 2.4.2 requires each route to set its own document title. 2.5.8 requires pointer targets to be at least 24 by 24 CSS pixels, or spaced so that 24-pixel circles centred on two of them do not overlap. 3.3.8 requires that authentication keep working with password managers, which here means keeping every `autocomplete` token correct and never blocking paste.

## Lint coverage

`web/` has no ESLint. Oxlint implements the `jsx-a11y` ecosystem as a built-in Rust plugin, off by default, and that is the whole of the mechanical guardrail. `.oxlintrc.json` enables the plugin in its `plugins` array, which overwrites the default plugin set, so that array has to list every plugin the repo uses. The documentation also shows a `--jsx-a11y-plugin` CLI flag for a one-off run; the repo configures the plugin in the file so editors, `pnpm lint` and CI see the same set.

The config names all 35 rules at `error` severity rather than trusting the plugin's category default, so the set cannot drift when oxlint moves a rule between categories. They group as follows.

| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Names and text alternatives     | `alt-text`, `anchor-has-content`, `control-has-associated-label`, `heading-has-content`, `iframe-has-title`, `img-redundant-alt`, `label-has-associated-control`, `media-has-caption`                                                                                                                                 |
| Links, controls and interaction | `anchor-is-valid`, `click-events-have-key-events`, `interactive-supports-focus`, `mouse-events-have-key-events`, `no-interactive-element-to-noninteractive-role`, `no-noninteractive-element-interactions`, `no-noninteractive-element-to-interactive-role`, `no-static-element-interactions`, `prefer-tag-over-role` |
| ARIA correctness                | `aria-activedescendant-has-tabindex`, `aria-props`, `aria-proptypes`, `aria-role`, `aria-unsupported-elements`, `no-aria-hidden-on-focusable`, `no-redundant-roles`, `role-has-required-aria-props`, `role-supports-aria-props`, `scope`                                                                              |
| Keyboard and focus order        | `no-access-key`, `no-autofocus`, `no-noninteractive-tabindex`, `tabindex-no-positive`                                                                                                                                                                                                                                 |

One of the 36 jsx-a11y rules oxlint ships is deliberately left off: `jsx-a11y/anchor-ambiguous-text`. It is the only jsx-a11y rule in the `restriction` category and the upstream plugin leaves it out of its recommended set as well. It bans link text such as 'click here'; every link in `web/src` names its destination today, so the rule would sit silent, and phrase choice is better handled in review than by a build failure. Add it when the app grows links whose text is a bare verb.

The guardrail bites already. With the plugin live, the first finding in this tree was in `web/src/components/notice.tsx`, which now renders its message in an `output` element (`notice.tsx:5`) instead of a paragraph carrying an explicit status role. `output` carries the status role implicitly, so the audit finding about that component is unchanged; the point is that the rules are enforcing something real on day one.

Provenance, because the names had to be right before anything was pinned. The rules reference at `https://oxc.rs/docs/guide/usage/linter/rules` lists 36 jsx-a11y rules, 35 in the `correctness` category and one in `restriction`, and records every one of them as added in oxlint v1.65.0 or earlier. The `configuration_schema.json` shipped inside the installed `oxlint` package, 1.85.0, which is what `pnpm-lock.yaml` resolves `^1.81.0` to, names the same 36 identifiers and accepts `jsx-a11y` as a plugin name. The audit below is a reading of the JSX, not linter output.

Two things limit what those rules can reach. Attribute values that arrive through props are invisible to them: `TextField` hands `autoComplete` to its input as an identifier rather than a literal (`text-field.tsx:31`), so `autocomplete-valid` has nothing to read. And a component that hides its element behind a prop is opaque to the rules; oxlint's schema does expose a `jsx-a11y` settings map, holding `components`, `attributes` and `polymorphicPropName`, for mapping such components onto the elements they render, and it is empty today because the components in `web/src` render their real elements directly.

## i18n conventions

- Strings live in one flat object in `packages/i18n/src/en.ts`. Keys are literal dotted names such as `'settings.world.walk-speed'`; they are not nested paths, and nothing nests objects under them.
- `keySeparator: false` (`packages/i18n/src/index.ts:13`) is what makes that work: i18next must never split a key on its dots. A key still has to be spelled exactly as `en.ts` spells it, in both files, because a mismatch ends up printing the raw key.
- Every user-facing string goes through `useTranslation`, re-exported from `@floorwalker/i18n` (`packages/i18n/src/index.ts:18`) rather than imported from `react-i18next` directly, so there is one initialised instance. No literal user-facing string belongs in JSX.
- `en` is the only locale (`packages/i18n/src/index.ts:7-11`), and it is also the fallback. Interpolation (`{{name}}`) is in use, for example `'world.seated-at': 'Seated at {{project}} · {{model}}'`; values are formatted before they are passed in (numbers and dates with `Intl` in the reader's locale), and joined phrases such as "model · tokens" are keys too, never string concatenation. There is no pluralisation or context use yet; the first one that arrives should follow i18next's own conventions rather than a local invention.

A translated string is not automatically an accessible name. A paragraph printed above a control is a printed label, not an accessible one: nothing in the markup ties the two together, so assistive technology reads them as unrelated text. When a control needs a name, the translated string has to reach the attribute or the element that creates the name: wrap the input in its label, or pass the string to `aria-label`, as Settings' sliders and switches do. Descriptions follow the same rule; a `dl` associates a term with its value.

The labels in `en.ts` are written as instructions ('Enter your email.', `en.ts:28`), and because a wrapping label is also the accessible name, that instruction is what a screen reader announces for the field. It works, but a name that identifies the field serves the user who lands on the input directly, so write new labels as names and put any instruction in a hint the field points at.

## Theme and tokens

`web/src/styles/theme.css` is the only place a colour lives. It is imported from `index.css` after `tailwindcss` and `@heroui/styles`, and it writes the design lock's values onto HeroUI v3's semantic variable names in two mode blocks — `:root, .dark, [data-theme="dark"]` and `.light, [data-theme="light"]` — then maps them into Tailwind's `--color-*`, `--text-*`, `--radius-*` and `--shadow-*` namespaces with one `@theme inline` block, so a utility resolves through the mode block rather than a build-time literal. `@custom-variant dark` is defined against the same selectors, so `dark:` follows the switch, and `color-scheme` comes from the mode block rather than from a utility. The repo's values win over the package's own blocks in both modes because this file is imported after the package and is unlayered; the light block is written second because the two selector lists carry equal specificity. ADR-0006 records why the kit's names are the repo's names; ADR-0007 records the switch.

Screen code follows four rules.

- Use the token utilities. No literal colour anywhere in `web/src`: no hex, no `rgb()`, no arbitrary `[#...]` value.
- `dark:` is reserved for what no token can carry — an image asset, a shadow, a gradient. Anything a pair of mode values can express belongs in the theme file.
- `prefers-color-scheme` appears only inside `web/src/theme/`, never in a component or a page.
- Contrast is checked against the token pair actually in use, in both modes. Every figure in the baseline below was computed from the literals and has to be re-derived.

`--raised`, `--separator-strong`, `--accent-ink`, `--danger-ink`, `--focus` and `--faint` are the repo's own names, in the kit's bare style, because the package declares no counterpart for them. `--danger-ink` is the one role the lock names no value for, so it derives from its neighbour: `color-mix(in oklab, var(--danger) 12%, var(--background))`, which lands dark ink on the light danger fill in dark mode and the inverse in light. `--overlay` is the surface a floating component is drawn on, which is the top of the elevation stack: the locked `raised` step in dark, and `surface` in light, where `raised` is a recessed fill rather than an elevated one. The kit's pair variables follow the lock too, so kit components read it: `--accent-foreground`, `--danger-foreground` and `--success-foreground` take the ink values, `--surface-foreground`, `--overlay-foreground`, `--field-foreground`, `--default-foreground` and `--segment-foreground` take `--foreground`, `--field-placeholder` takes `--faint`, `--border` takes `--separator`, and `--surface-secondary`, `--surface-tertiary`, `--default` and `--segment` derive from their neighbours with `color-mix` or an alias rather than a new literal. `--link` takes the accent.

### Type, radius and elevation

The locked ladder is the whole of the type scale: `text-xs` 12.5px for meta, labels and hints; `text-sm` 14px as the default UI size, which `body` takes; `text-base` 16px for card and section headings; `text-2xl` 24px for page titles; `text-3xl` 30px for the auth hero title. `text-mono` is a utility rather than a scale step: 13px monospace for values, keys and legal metadata, which is the only place monospace appears.

Radii are the locked 6/9/12/16/22px steps plus the pill: `rounded-xs` 6px, `rounded-sm` 9px, `rounded-md` 12px for inputs, buttons and chips, `rounded-lg` 16px for cards, `rounded-xl` 22px for overlays, `rounded-pill` for segmented controls and chips. The kit's field radius is pinned to the 12px step as well, so a kit field and a repo field agree.

Elevation is three steps: `shadow-control` for controls and pills, `shadow-card` for grouped cards, `shadow-overlay` for overlays. The kit's own `--field-shadow`, `--surface-shadow` and `--overlay-shadow` point at the same three, so kit components carry the repo's elevation.

Spacing stays on Tailwind's defaults, and motion is the lock's two steps: `--default-transition-duration` is 140ms for state colours, while the press offset on a control moves at `--press-duration` 100ms through `active:duration-press`. The locked density numbers are ordinary spacing utilities: 36px controls are `h-9`, the 30px small size is `h-7.5`, rows are `px-4` and `py-4`, page padding is `p-10` collapsing to `p-6`, and 26px between groups is `gap-6.5`. The focus ring is `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-focus`, and theme.css removes animation and transition under `prefers-reduced-motion: reduce`.

### The switch

`web/src/theme/theme.ts` owns the resolved mode. `getPreference` and `setPreference` read and write the device-local `localStorage['ag-theme']` key — `light`, `dark` or `system` — `resolvedMode()` answers what is painted, and `subscribe` is read through the `useThemePreference` and `useResolvedMode` hooks. Dark is the preference and the resolved mode when the key is absent, unrecognized or unreadable, which is why a first visit is dark rather than following the device. `startTheme()`, called from `main.tsx`, arms it for the whole document: an operating-system change repaints while the preference is `system`, and a `storage` event from another tab applies here. The resolver writes the resolved name to both `class` and `data-theme` on `<html>`, which is the kit's own contract and what the `dark` variant is defined against. Nothing animates across a theme change.

First paint never flashes light. `web/index.html` ships `class="dark" data-theme="dark"` statically, and `vite.config.ts` inlines `web/src/theme/theme-preload.js` into `<head>` ahead of the module script, substituting the storage key it imports from `web/src/theme/preference.ts`, so the key is written once and the snippet cannot drift from the module. The snippet duplicates the resolution rule and nothing else: it rewrites both attributes, or leaves the static dark state alone when storage throws.

Replacing the literals is contextual, because each one does several jobs. `#efeae1` is the page canvas and also the ink on the black chrome; `#1a1814` is the ink on the canvas, the chrome and footer fill, the borders and the focus outlines; `#322e28` is the hover fill of the primary button. Each occurrence takes the token for the job it does there — canvas to `bg-background`, ink to `text-foreground`, fills to `bg-surface`, borders to `border-separator`, outlines to `outline-focus` — rather than a single substitution per literal.

## Baseline audit

Method: every page in `web/src/pages` was read as JSX along with the components it renders from `web/src/components`, and each colour claim was computed from the literal values in those files with the WCAG relative-luminance formula rather than measured in a browser. The marketing landing page was deleted while this ticket was in flight, so `web/src/pages/index.tsx` is now a redirect page and `hero.tsx`, `comparison.tsx`, `how-it-works.tsx`, `includes.tsx` and `engineers.tsx` no longer exist; `index.tsx` is audited in its current redirect form. Nothing was executed to produce this table, and it reads the working tree as it stood while it was written, including the concurrent edits to `en.ts`, `notice.tsx` and `index.tsx`.

Four of the findings moved with that work. F2's four pages now put the sentence in the field's `aria-describedby` and set `aria-invalid` on that field; the message names the field it belongs to. F3's password rule is stated as a hint on register and change-password instead of arriving after a failed submit. `Notice` is never unmounted while a screen is up, so a result that arrives after submit lands in a region that already existed. `AuthLink` draws its underline in the accent at full strength. ### Shared findings

**F1. Page title, 2.4.2 (A). Resolved by ticket 13.** `web/index.html:7` used to give the document one title, `Template`, for every route, and nothing under `web/src` set `document.title`, so a title that named the product said nothing about the page that was open. Every route now sets its own through `useDocumentTitle` (`web/src/components/document-title.ts`), which each page calls with its own `title.*` key and which writes `${title} · ${product}` off `index.wordmark`; the five legal pages pass the `title` out of their document's front matter instead, through `legal-page.tsx`. The static `Floorwalker` in `index.html` survives as what the browser paints before the first route commits, and no route outlives it. The F1 rows in the per-page table below remain as the finding stood when the audit was written.

**F2. Error identification, 3.3.1 (A). Fails on four pages, unsure on one.** Errors arrive as a single translated sentence in the shared `Notice`, and nothing ties that sentence to the field it concerns: the only ARIA attributes in the JSX under `web/src` are `aria-label` at `site-footer.tsx:14` and `aria-hidden` at `code-list.tsx:9`, so no input ever receives `aria-invalid` or `aria-describedby`. On a page with two fields and one generic message, the user cannot tell which field was rejected. That is a failure on register (`register.tsx:28-36` over `register.tsx:50-65`), change-password (`change-password.tsx:25-33` over `change-password.tsx:46-61`), two-factor-challenge (`two-factor-challenge.tsx:32-35`, which reports `error.invalid-field` when both or neither of two fields is filled) and two-factor-disable (`two-factor-disable.tsx:29-32`, the same shape). Login is unsure: its message is the generic `error.invalid-credentials` (`login.tsx:31`), and a deliberately vague credential error is a recognised security posture even though it is unassociated with either field.

**F3. Labels or instructions, 3.3.2 (A). Fails on two pages, unsure on two.** Every input has a label, because `TextField` wraps its input in one (`text-field.tsx:25-36`). What is missing is the format a field requires. A new password must be at least 8 characters and at most 128 bytes (`api/src/auth/password.rs:10`), and the only feedback is the generic `error.invalid-password` ('That password is not allowed.', `en.ts:113`) after submit, so register and change-password state no requirement up front. The two-factor pages carry a rule that exists only in the code, that exactly one of their two fields must be filled (`two-factor-challenge.tsx:30-35`, `two-factor-disable.tsx:27-32`), while the page's only instruction is `challenge.pending` ('This sign-in is not finished.', `en.ts:63`); those two are unsure, because their field labels do say what to type.

**F4. Status messages, 4.1.3 (AA). Unsure on eleven pages.** `Notice` returns `null` while there is no message (`notice.tsx:2`), so on these pages the live region enters the DOM already holding its text, and a region is only reliably announced when it exists first and then changes. Several pages do render a populated `Notice` in their pending branch, for example `login.tsx:49`, but that is a different element instance and it unmounts when the gate opens. `two-factor-challenge.tsx:62` is the shape that works, because it renders the region with `challenge.pending` as its default text. The behaviour differs between browser and screen-reader pairs and could not be tested here, so this stays unsure rather than failed.

**F5. Non-text contrast, 1.4.11 (AA). Resolved by ticket 12, with one figure carried forward.** The underline used to be drawn at 40% opacity, which composited below 3:1 on the cream surface. The link is now drawn in the accent, underline included, so one pair carries both the text and the identifier, and it is re-derived here from the tokens rather than from literals. Against the card the link sits on (`surface`), dark `#5aa2ff` is 6.7:1 and light `#1d4ed8` on `#ffffff` is 6.7:1; against the canvas (`background`) the same pairs are 7.4:1 and 6.2:1. Hovering moves the pair to `accent-hover`: 8.5:1 dark and 8.1:1 light against `surface`. The footer's links are the same component on `surface`, so the same figures hold there. The text pair is not in question either: `foreground` on `surface` is 15.1:1 dark and 18.1:1 light, and the primary button's `accent-ink` on its `accent` fill is 7.0:1 dark (`#04152e` on `#5aa2ff`) and 6.7:1 light (white on `#1d4ed8`), rising to 8.8:1 and 8.1:1 against the `accent-hover` fill. The row separators (`separator` on `surface`) measure 1.3:1 in both modes and `separator-strong` 1.8:1 in both, but they separate rows rather than identify a control, so the reading above stands unchanged. The one boundary the audit records below 3:1 is the field hairline, `separator` on `field`: 1.2:1 in both modes. It is the lock's deliberately low-contrast boundary, the field is identified by its label, its fill and the accent ring, and a reviewer who reads the boundary as the sole identifier would call it a failure rather than decoration. The invalid state clears the bar: `danger` on `field` is 5.8:1 dark and 6.2:1 light.

### Criteria the pages pass

Worth recording, because it is what the retheme must not break. Keyboard reachability passes everywhere: every control is a native `input`, `button` or `a`, there is no `tabindex` anywhere in `web/src`, and the only `onClick` sits on a real `button` (`home.tsx`, `submit-button.tsx`). Focus visibility passes everywhere: the auth pages and their primitives set an explicit outline, and on the five legal pages the browser's default ring is still there, because Tailwind's preflight does not remove it. Landmarks and headings pass: `AuthShell` supplies a `header`, a `main` and one `h1` per page, the legal pages supply their own (`tos.tsx:7-8`), and `SiteFooter` adds a `contentinfo` with a named `nav`. Accessible authentication passes: every credential field carries the right `autocomplete` token (`login.tsx`, `register.tsx`, and `one-time-code` on the five TOTP fields), which is what lets a password manager complete it. Target size passes as far as the source shows: inputs and buttons are 36 pixels high (`text-field.tsx`, `submit-button.tsx`) and the stacked text links sit about 34 pixels apart centre to centre, over the spacing exemption's 24. No motion criterion fails, because nothing moves.

Two smaller observations rather than failures. The page-local `nav` elements on login (`login.tsx:76`), home (`home.tsx:65`) and enroll (`two-factor-enroll.tsx:70`) carry no accessible name, which is a gap against the ARIA authoring practice for landmarks rather than against 2.4.6. And `verify-email` asks for the password a second time (`verify-email.tsx:63-70`), which is exempt from 3.3.7 as a security re-check rather than treated as redundant entry.

## What lint cannot catch

- Contrast of any kind, 1.4.3 and 1.4.11. No rule reads computed colour, alpha compositing or the token pair in use.
- Anything that needs a rendered page: target size against real boxes (2.5.8), reflow at 320 pixels and at 400% zoom (1.4.10), text spacing (1.4.12), focus not obscured (2.4.11), and whether a scrollable region can be reached and left with the keyboard (2.1.1, 2.1.2).
- Whether a live region actually announces, 4.1.3. The rules see the element and its role; they do not see the browser and screen reader speaking.
- Whether a name is meaningful. `anchor-has-content` can see that an `a` element has content, but nothing can tell that the translated string inside it reads 'click here'. That gap is the reason `anchor-ambiguous-text` exists, and it is the one rule this config leaves off.
- Values that arrive through props. A wrapper component that hands `autoComplete` to its input as an identifier rather than a literal leaves `autocomplete-valid` nothing to check; the same is true of any attribute a wrapper component forwards.
- Custom components. The `jsx-a11y` settings map in oxlint is empty, so the rules judge the element written in the JSX and not what a component renders for a different element.
- The document itself. `html-has-lang` and `lang` only see an `html` element written in JSX; `web/index.html:2` and `web/index.html:7` are outside the linter, which is why the 2.4.2 failure above is invisible to it.
- Instructions, plain language and error association beyond shape. `label-has-associated-control` checks that a label points at a control, not that an error message names the field (3.1.5, 3.3.1, 3.3.2).
- Tab order (2.4.3). The rules see attributes, not the order focus actually moves in.

Browser-based accessibility testing is out of scope for this effort, so these gaps are covered by review against this document, not by tooling.

## What this baseline does not establish

Every line above comes from reading source. There was no browser, no screen reader and no axe run, so the measurements that need layout, target size, reflow and text spacing, are marked unsure or left to the screen tickets. The colour claims are no longer read off literals in the JSX: the token layer in `web/src/styles/theme.css` is the only place a colour lives, and every figure above was re-derived from the token pairs actually in use, in both modes, with the WCAG relative-luminance formula, so the numbers describe the current tree rather than the pre-token one.
